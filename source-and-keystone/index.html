Source and Keystone: two design systems, rebuilt with AI

The two largest design systems I've worked on, rebuilt first as interactive design artifacts, then as real front-end code with Storybook and docs from one source.

  • Two systems
  • 115 components
  • 111 stories
  • Four brands
  • Light and dark
  • LTR and RTL

As design artifacts

All of this was built as design artifacts: interactive, clickable, running in a browser, but not code. Worth being clear about that, because turning them into real code came next.

None of it was missing when I first built these systems: theming, propagation, documentation and direction all shipped back then, in design and in code, in use across markets. I'm going back through that work to see what the same job costs now, so what's below is the same capabilities, with the cost of having them taken off.

Every design system I've worked on had documentation that lagged the components by a few days or weeks. These structurally can't.

Brand theming. Ask for a new brand and it arrives themed: every component, every state, both directions, in minutes. Adding a brand is a conversation rather than a week of work.

Dark mode. Built across both systems in an afternoon. It's the one thing here that never went live first time: specified, costed and cut every time, not because anyone argued against it but because nobody ever got to see it or play with it.

Direction. Flip the toggle and the whole system turns over, docs and products. Back then RTL was a project of its own, with layouts mirrored by hand and icon flipping that was meant to be automatic and reliably wasn't. Now the only work left is the checking, and anyone on the team can see it working for themselves.

Also

  • Documentation with search that finds a component by what it does, and every state, theme and direction reachable from the page you're already on, so the system explains itself instead of needing me in the room
  • Four products on top: three user-facing experiences on one system, a consumer app on the other. Working journeys assembled from the system's own components, so a change in the source of truth changes the product
  • Audits built in rather than bought: what isn't linked back to the system, accessibility across both themes, whether the docs still match the components. A check you run before committing something, not a report once a month
  • How the files are organised matters more than how well you prompt. It's the same discipline that stops a human team diverging

What links these isn't capability, it's demonstration. The work that sat between we support this and here, look (the demo, the sandbox, the maintained example) was always the first thing cut when the quarter got tight. That work is now a few hours, so it doesn't get cut.

Into code

Into code. I've rebuilt the two largest design systems I've worked on as real front-end code: the same two shown as design artifacts above. 115 React components between them, each with a token source that compiles to CSS variables rather than sitting as a flat file, and four brands themed light and dark on one of them. Both built out from my own design files rather than from anyone's codebase.

Storybook as the test harness. 111 stories across the two, and every one runs as a test in a real browser. Break a component and the run fails, rather than waiting for someone to notice. Brand, theme and direction all switch from the toolbar, so any component can be checked in any of the ten theme combinations, LTR or RTL, without leaving the page. Everything above lived in design artifacts; this is the first version an engineer could open, read and argue with.

Docs from the same source. Both documentation sites import the same components and tokens the products use, so each system has one source feeding the docs, Storybook and the apps. Every design system I've worked on had documentation that lagged the components by a few days or weeks. These structurally can't.

Also

  • Several app prototypes covering different user types and journeys, built in Claude Code from the system's own components rather than drawn. Starting a new one is now an afternoon, because the parts underneath are real
  • A product idea I'd shared with a former colleague, written down as a vision and then actually built on Chakra rather than a component library from scratch, because the question was whether the idea worked, not whether I could make buttons. Before, it would have stayed a conversation
  • Accessibility violations report per story in Storybook, checked as you build rather than audited at the end

Not yet. No backend. There's a sign-in screen, but nothing behind it checks anything. No data layer worth the name. These are front-ends: real components, real tokens, real states, nothing behind them. Worth saying plainly, because "I built a product" can mean very different things.

Next. Two things I know are missing.

  • Versioning: no releases, no changelog, nothing for anyone to pin to. Fine for one person, untenable the moment a second team builds on it
  • Visual regression, properly or not at all: scaffolded and unused, so either wire it up or take it out

After those, the questions that need other people in the room: where governance sits, what stops drift, and what a review looks like when the thing being reviewed took ten minutes to make.
